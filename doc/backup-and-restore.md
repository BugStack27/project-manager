# 数据备份与恢复 — 决策记录

> 状态：✅ 已验收（2026-10-27）

## 1. 目标与范围

应用要能看见并使用自动备份，而不是只写不读：列出最近 7 天每日快照与手动安全备份，两步确认后先保全当前库、再用快照覆盖 `db.json` 并自动重启；有活跃命令（含已分离但仍存活的进程）时阻止恢复。启动时 `db.json` 解析失败不再静默换成空库——保留原文件、本次运行只读，界面顶部提示并提供恢复入口。

不做：立即备份 / 删除快照 / 快照预览与差异对比 / 恢复 `runs/` 日志 / 跨机迁移 / 调整自动备份策略 / 把恢复能力暴露到 MCP。

## 2. 关键决策

| 决策点 | 结论 | 理由 |
|------|------|------|
| 入口位置 | 侧栏底部「设置与数据」→「数据」组 →「备份与恢复」 | 低频操作不占导航；按用途分组后与通知 / 记录入口分开 |
| 恢复生效方式 | 覆盖后 `app.relaunch()` + `app.exit(0)` 自动重启 | 跳过 before-quit → shutdown 的保存，避免内存旧库写回 |
| 有命令在运行 | 用 `runner.isActive` 判断，已分离且宿主存活的进程同样拦截（409 `commands_running`），提示先到启动台停止 | 进程退出会把内存旧库写回，静默覆盖恢复结果；分离进程不被 `isRunning` 算到，2026-10-31 修正 |
| 恢复前保全 | 当前库复制为 `backups/manual-YYYYMMDD-HHmmss.json`，不参与 7 天清理 | 恢复可撤回；同秒重名追加序号 |
| 快照可恢复性 | 列表逐个解析，坏文件标「无法解析」且不可选；后端恢复前二次校验 | 坏快照绝不覆盖 `db.json` |
| 两步确认 | 沿用 `DangerButton`；切换选中项即重置已武装态 | 危险写操作；避免确认落到另一份快照 |
| 列表信息 | 日期 + 大小 + 项目 / 需求 / 命令数 | 直接回答「哪份快照可用」 |
| 损坏时启动 | 保留原 `db.json`、不写空库，锁写进入只读空库模式，顶部常驻提示条 | 写空库会掩盖损坏，用户误以为数据丢失 |
| 损坏恢复前保全 | 损坏库另存 `db.json.broken-<时间戳>`，不放进 `backups/` | 原文件需留档；坏数据进列表只会制造噪声 |
| 损坏判定口径 | 读取失败、JSON 解析失败、根节点不是对象（含数组）都算损坏 | 合法 JSON 但结构不对同样无法使用 |
| 提示条出口 | 不可关闭，只给「数据文件」与「备份与恢复」 | 本次运行改动不会落盘，必须促使处理 |

## 4. 关键修正与教训

- **恢复后重启仍把旧库写回** → 恢复后必须锁写让 `save()` 短路，重启必须走 `app.exit` 跳过 `shutdown()`。
- **「有命令在运行」不能只看 live 句柄** → 已分离但宿主存活的进程仍会写回旧库，恢复守卫必须用 `runner.isActive`。
- **坏快照覆盖 `db.json`** → 恢复前完整解析校验；列表禁用与后端拒绝两层拦截缺一不可。
- **启动解析失败直接写空库** → 原文件被覆盖、界面毫无异样；改为保留原文件 + 锁写 + 只读空库，并暴露状态供界面提示。
- **合法 JSON 数组被当成正常库** → 根节点类型要显式校验，否则字段补全会把数组当对象用。
- **损坏副本放进 `backups/` 会污染快照列表** → `listBackups` 会把坏文件列成「无法解析」项；改用 `db.json.broken-*` 留在数据目录根。
- **危险按钮的确认态跨选中项残留** → 确认态必须随选中对象重置（绑定选中项作 key）。
- **提示条局部按钮底色覆盖了 `.primary`** → 给局部按钮加底色时要排除主按钮，否则主按钮白字白底不可见。

## 5. 已知边界

- 恢复是整库覆盖，只恢复 `db.json`，不恢复 `runs/` 日志，不做合并。
- manual 安全备份长期保留，暂无清理 / 删除入口。
- 损坏检测只在启动时做一次：运行期间数据文件被外部改坏不会立即提示，需重启后进入损坏模式。
- 损坏模式下本次运行的改动不会落盘；需用户自行选快照恢复，或退出后手工处理原文件。
- 没有任何可用快照时只能引导到数据目录，不提供兜底复制。
- `backups` / `restoreBackup` / `dataStatus` 不暴露到 MCP。
