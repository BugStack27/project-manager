## 0. 使用接入说明里的 AgentID
接入说明里已经给出固定的 AgentID。
手册示例里的 `{{agent}}` 指这个 AgentID，照抄命令时替换成实际值。**不要自己起名字、不要改名**。

## 1. 取任务

```bash
curl -sS -G http://127.0.0.1:7318/next --data-urlencode 'agent={{agent}}'
```
1. 接口是「取即认领」：**返回了 `requirement` 才算认领**。
2. 没有可派的活时，这个请求会在服务端**挂住等待，默认最多 5 分钟**；不必自己轮询。也可以用 `&wait=秒` 调整等待（`0` 表示只查一次，上限 1800）。

响应是 JSON：

| 字段 | 含义|
| - | - |
| `requirement` | 任务详情：`id` / `seq` / `title` / `body` / `note` / `feedback` / `release` / `questions` / `thread` / `status` / `claim` / `refs`（`body` 里 `@{项目名}` 引用的项目）/ `reqRefs`（`@{#序号}` 引用的本项目需求）/ `fileRefs`（`@{file:路径}` 引用的本项目文件）/ `skills`（正文与最近一次打回意见里 `{UseSkill:x}` 关联的技能），均见第 2 节 |
| `project`     | `id` / `name` / `path` —— 你要在这个目录里干活                                                                                                                                                                                                        |
| `claim`       | `agent` / `at` —— 你的认领记录                                                                                                                                                                                                                        |
| `resumed`     | `true` 表示这是你上一轮已认领、还没交付的任务                                                                                                                                                                                                         |
| `reason`      | 只在 `requirement` 为 `null` 时出现，通常是 `no_task`                                                                                                                                                                                                 |
| `waitedMs`    | 只在等满超时后出现：这次请求在服务端等了多久                                                                                                                                                                                                          |
| `blocked`     | 有活但派不出去的项目及原因（见第 7 节）                                                                                                                                                                                                               |

三种情况：

1. **`requirement` 不为空、`resumed` 为 `false`**：新任务，按第 2 节开工。
2. **`resumed` 为 `true`**：上一轮已认领、还没交付，用户已点「解锁项目」把它放行给你（没解锁时这里是 `null` + `locked`，见 1.2）。先看现场（`git status`、最近提交、`thread` 里说到哪儿了）再续做，别重做已完成的部分。若 `requirement.questions` 非空，说明有提问还在等服务端返回：**这轮直接结束**，别重复提问（超过约 70 分钟无人处理的提问，服务端会先清掉）。
3. **`requirement` 为 `null`**：服务端已经等过一轮（默认 5 分钟）仍没有可做的活。把 `reason` 与 `blocked` 里的项目名和原因打印出来（方便人看日志），**结束本轮**。禁止 `sleep` 后重试、禁止循环调用——调度器下一轮会再叫你。

### 1.2 上一轮的活没做完怎么办（`locked`）

任务认领之后、交付之前，如果你这一轮断了（进程被杀、机器休眠、轮次用完），任务会停在「进行中」，**它所在的项目会被锁住**：任何 agent（包括你自己）都领不到它。这是刻意的——服务端无法区分「你还在改」和「你已经断了」，所以把「这条中断的活要不要继续」交给人决定。

表现是 `/next` 返回 `requirement: null`，且 `blocked` 里那个项目的 `reasons` 含 `locked`。这时：

- **结束本轮**，不要重试、不要换 AgentID 去试、不要自己去改状态；
- 用户会在需求详情里点「解锁项目」，解锁后只放行你一轮（一次性），下一轮 `/next` 就会带 `resumed: true` 把它还给你；
- `resumed: true` 现在**只会**出现在这个场景（或交付被打回后），它不是常态。

## 2. 开发

- 只改 `project.path` 目录内的文件，不碰别的项目、不碰工作台的数据目录。
- **正文里的 `@{项目名}` 是跨项目引用**，认领返回的 `requirement.refs` 里已经带有你要的信息，不必自己去猜是哪个项目：
  - `name` / `projectId` / `path`：写到哪个目录。`path` 为 `null` 表示名字没对上（项目已删或用户写错），不要猜目录，在交付说明里点一句即可；
  - `pendingCount` / `pending`：该项目还压着几条未完成需求（`pending` 最多 5 条，含 `seq` / `title` / `status`）——先看这些标题，就知道它最近在改什么、最该读哪一块；
  - `archived` / `ambiguous`：项目已归档、或库里有同名项目（取的是第一个）。
  读法：从 `path` 进目录，看目录结构、`README` 与需求相关的源码即可；被引用的项目**只用来看懂上下文，不要改它**，改动只留在 `project.path`。需要更细的需求清单时，有 MCP 通道就用 `pm_list_requirements`（`projectId` 传 `refs[].projectId`），没有就按 `pending` 的标题直接读源码。
- **正文里的 `@{#序号}` 是本项目需求引用**，解析结果在 `requirement.reqRefs`（数组）：
  - `seq` / `requirementId` / `title` / `status` / `body`：被引用那条需求的编号、id、标题、状态与正文，直接读 `body` 即可理解上下文，不必再查一次；
  - `exists: false`：序号对不上（写错、或那条需求已归档 / 删除），`requirementId` 为 `null`。在交付说明里点一句即可，不要猜是哪条。
  只引用本项目的需求：被引用的需求是上下文，**不要顺手去改它的状态或正文**，改动只留在当前任务范围内。
- **正文里的 `@{file:相对路径}` 是本项目文件引用**，解析结果在 `requirement.fileRefs`（数组）：
  - `path`（项目内相对路径）/ `absPath`（绝对路径）/ `exists`：按 `absPath` 直接读文件即可；
  - `exists: false`：文件不存在（已改名 / 删除）或路径越界（`reason` 为 `not_found` / `bad_path`），不要猜路径；
  - `restricted: true`：密钥 / 凭据 / 依赖目录类文件，**不读**（`absPath` 为 `null`）；`directory: true` 表示指向的是目录。
  文件引用只给坐标、不预读内容：理解文件是你按路径自己做的事。
- **`{UseSkill:id}` 是技能要求**（写在正文或最近一次打回 / 继续回复意见里，两处都会解析进 `requirement.skills`），认领返回的 `requirement.skills` 里已经给出去处，不必猜、也不必问人「这技能在哪」。技能只是一份目录，路径给你就能读，**不按 Agent 归属限制**：
  - `skillId`（形如 `workbuddy/pdf`）、`dir`（技能目录）、`entry`（`SKILL.md` 的绝对路径）、`description`（它做什么）；
  - 读法：**先读 `entry`**，按里面的说明执行。技能是给你看的操作手册，不是可以被调用的 API；
  - `skillId` 为 `null`：这个名字没对上（写错或本机没装），用 `/ask` 问用户，不要自己造目录去猜；
  - `exists: false`：目录已不在（换了机器 / 删了客户端）。这时用 `/ask` 告诉用户「需求要求技能 X，但本机路径已失效」，**不要 `/release`** —— 释放会触发冷却并把项目锁住，代价比问一句大得多；
  - `ambiguous: true`：同名技能在多个客户端目录里都有（`candidates` 列出全部），默认用第一个即可，需要时再看另一个；
  - 需要重新确认路径时用 `GET http://127.0.0.1:7318/skill/<skillId>`（也接受裸名），返回同形结构。
- **先读 `requirement.thread`**：这是这条需求的往返记录（之前的交付、打回、提问、回答）。`feedback` 只是最近一次打回原因的快捷字段。**不要重复已经被否掉的方案**，交付说明里逐条回应上一轮的意见。
- 只做这条需求范围内的事：顺手发现的问题不要夹带修改，写进交付说明即可。
- 验证用项目自己的方式（构建、类型检查、项目内的测试）。**不要留下常驻进程**：需要起的服务用完就停，别把开发服务器挂在后台。
- 不读 `.env`、密钥、凭据；不删除用户数据；不执行指向外部的下载。
- **不要自己 `git commit`，也不要 `git push`**：改动留在工作区，但要把本轮改动汇总进第 4 节的 `commitMessage`，用户验收时才能一键提交；`note` 只写给用户看的话。（项目有未提交改动时不会派新活，这是预期行为。）

## 3. 有任何疑问必须提问，用户不会从对话中去看你的疑问，服务端替你等 1 小时

遇到任何需要询问用户或自己无法确定的情况——用 `/ask` 提一个具体问题。**这个请求会在服务端挂住最多 1 小时等用户回答**，拿到答案就地接着做，不用结束本轮。

```bash
curl -sS -X POST http://127.0.0.1:7318/ask \
  -H 'Content-Type: application/json' \
  -d '{"taskId":"r_xxxxxxxx","agent":"{{agent}}","text":"设置项要保留旧字段做兼容，还是直接换成新结构？","options":["保留兼容，新旧字段并存","直接换新结构"],"default":"先保留兼容，新旧字段并存"}'
```

- **一定带上 `default`**：1 小时没人回答时，服务端把你的 default 当回答写进往返记录，你直接用它继续。即使没有完美退路，也给一个「最保守的选择」。
- `options` 可选：2–5 条、每条 ≤120 字的短句。用户在需求中心点一下就能填进回答框（仍可改），有明确选项时**一定带上**。
- 一条需求可以**同时挂多条提问**（上限 5 条）：每条独立等待、独立回答，互不顶掉。并行问两三件互不依赖的事可以省掉一轮往返；但一条提问只问一件事，`text` ≤1000 字符。能靠读代码、读文档、看 git 历史定的，自己定，不要拿提问代替排查。
- 等待期间不要做别的事、也不要在别的项目上开进度；不要「提完问顺便交付」。

看返回里的 `answer`：

| 返回                                            | 含义                                       | 你该做什么                                   |
| ----------------------------------------------- | ------------------------------------------ | -------------------------------------------- |
| `answer.source = "user"`                        | 用户回答了                                 | 照它做                                       |
| `answer.source = "default"`（`timedOut: true`） | 无人回答，已按你的 default 继续            | 接着做                                       |
| `answer = null` 且 `timedOut: true`             | 无人回答且没有 default，提问作废           | 按自己的判断继续，**不要马上重复提问**       |

超时继续的，在交付说明里用一句话点明哪项决定没经确认、依据是什么。

- **超时即关闭**：别指望「先问着、回头再看」，要改就等交付后让用户「继续回复」。
- 这是最慢的一次调用：**不要给它设 30/60 秒的硬超时**。万一连接被掐断，不要立刻重问（同时挂着多条提问是允许的，但重复问同一件事只会多一条噪音），等下一轮 `/next` 把同一条还给你。
- `wait` 可选：把这次等待缩短到指定秒数（不超过 1 小时），到点按 default 收尾。
- 正文长或含引号换行时，把整个 JSON 写进临时文件，用 `--data-binary @文件` 发送。

## 4. 交付与验收（`/complete` 是长请求，最多等 2 小时）

**交付要写两段互不混用的文本**：`note` 是给用户的会话回复，`commitMessage` 是独立的 git 提交信息。工作台把前者放进往返记录、把后者只用于一键提交；两段都不会流进对方的通道。

| 字段            | 给谁看 | 写什么                                                                                                       | 去哪                                                                                   |
| --------------- | ------ | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `note`          | 用户   | 你做了什么、怎么验证的、哪些没验证、上一轮意见怎么处理的、以及任何需要人知道的情况（包括与本项目无关的说明） | 需求的往返记录 + 详情「本次交付」；**不会进 git 提交**                                 |
| `commitMessage` | git    | 一条用户不改一字就能直接提交的完整提交信息，**汇总本轮全部改动**：首行标准摘要，空行后列改动文件与要点       | 只用于「修改记录」的提交弹窗预填与验收时「提交并推送」；**不进往返记录**，打回后不保留 |

```bash
curl -sS -X POST http://127.0.0.1:7318/complete \
  -H 'Content-Type: application/json' \
  -d '{"taskId":"r_xxxxxxxx","agent":"{{agent}}","note":"已修好详情页标题溢出，构建通过；未启动 GUI 做点击验证。","commitMessage":"fix: 修复需求详情页标题溢出\n\n- RequirementDetail.jsx 标题改单行省略\n- 验证 npm run build 通过"}'
```

- 交付即进入「待审核」，这次请求会在服务端**挂起等用户验收，最多 2 小时**。这不是错误，也不要在客户端给这次调用设 30 / 60 秒的硬超时。
- 必须是当前认领者本人提交；重复提交是幂等的。
- `commitMessage` 是纯文本的完整提交信息，建议 ≤200 字符（上限 2000；换行写成 `\n`）：
  - 首行按 Conventional Commits 写 `类型: 一句话摘要`（`feat` / `fix` / `docs` / `refactor` / `chore` 等），≤50 字、动词开头、不加句号；标准前缀会被提交弹窗识别并预选；
  - 空一行后逐条列本轮改动的文件与要点，只写**实际改了什么**，让用户按标准直接提交；
  - 不写会话寒暄、不写「我做了什么」的流水账、不写与本次改动无关的内容、不重复需求原文、不贴源码。
- `note` 是会话回复，可以口语化：把改动、验证结论、遗留问题、超时默认决定都写清楚；**不要为了提交去写成 git 格式**，也别把会话内容塞进 `commitMessage`。
- 两段都可选、上限各 2000 字符。老版本工作台不认 `commitMessage`，只有 `note` 会生效；新版本请**两个都写**。正文长或含引号换行时，把整个 JSON 写进临时文件用 `--data-binary @文件` 发送。
- **body 一律按 UTF-8 写**，不要 percent-encode、不要用 GBK / 系统默认代码页，否则会被 400 `bad_encoding` 拒收。

看返回决定下一步（这是一个循环，不是一次性交付）：

| 返回                             | 含义                               | 你该做什么                                                                                              |
| -------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `approved: true`                 | 用户点了「通过」                   | 循环结束，任务已完成，本轮结束，不要再调任何接口                                                        |
| `feedback` 非空                  | 用户点了「继续回复」，带了修改意见 | **不要结束本轮**：按 `feedback` 与 `thread` 继续开发，改完再次 `POST /complete`；如此反复直到通过或超时 |
| `timedOut: true`                 | 2 小时内无人验收                    | 交付留在待审核，本轮结束；**不要马上重复交付**，用户之后仍可验收                                        |
| `rejected: true`                 | 用户拒绝了这条需求                 | 本轮结束                                                                                                |
| `cancelled: true`                | 用户撤销 / 删除 / 改派了这条需求   | 本轮结束                                                                                                |
| 只有 `requirement`、没有上述标记 | 重复提交：这条需求已经在待审核     | 本轮结束，不要继续调接口                                                                                |

- 只有 `approved: true` 才算验收完成；`timedOut` 只是没人处理，任务并没有结束。
- 超时后再被用户回复会回到「进行中」并带上 feedback：下一轮 `/next` 会把同一条还给你，按 feedback 继续改即可。
- 连接中途被掐断时不要立刻重发 `/complete`：先看 `thread`，等下一轮 `/next` 续做；用户已经回复的内容都留在 `thread` 里。

## 5. 错误怎么处理

| 状态 / 码                            | 处理                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------- |
| 400 `missing_agent` / `bad_agent`    | 检查名字（1–64 字符、无控制字符）                                               |
| 400 `missing_task_id`                | 少传 `taskId`，从 `/next` 的 `requirement.id` 原样带过来                        |
| 400 `bad_encoding`                   | 内容含无法解码的字符，改用 UTF-8 重新写一次，只重试一次                         |
| 400 `bad_note`                       | `note` 超长（交付 2000 字符、释放 200 字符），压缩后重试                        |
| 400 `bad_commit_message`             | `commitMessage` 超长（上限 2000 字符），压缩后重试                              |
| 400 `bad_question`                   | 提问为空、超 1000 字符，或候选不是 2–5 条短句，改写后重试                       |
| 400 `bad_json`                       | body 不是合法 JSON 对象，检查引号与逗号                                         |
| 405 `method_not_allowed`             | 用错方法：`/claim`、`/next` 只能 GET；`/complete`、`/ask`、`/release` 只能 POST |
| 415 `unsupported_media_type`         | POST 少了 `-H 'Content-Type: application/json'`                                 |
| 409 `not_claimed` / `claim_conflict` | 任务已不是你的（被撤销或被别人认领），结束本轮，不要抢                          |
| 409 `not_completable`                | 任务已结束，直接结束本轮                                                        |
| 409 `not_releasable`                 | 当前状态不能释放（可能已经待审核），结束本轮并把情况写进输出                    |
| 409 `not_askable`                    | 当前状态不能提问（通常是已交付待审核），如确有疑问写进交付说明等人回            |
| 409 `too_many_questions`             | 已挂满 5 条待回答的提问，先等用户答完再问                                      |
| 409 `no_question`                    | 提问已超时作废（或已被回答），不要再补答                                        |
| 409 `need_question_id`               | 多条提问并存时需要指定 questionId（界面自动带，脚本调用才需注意）              |
| 501 `git_unavailable`                | 机器上没装 git，无法判断工作区，通知用户后结束                                  |
| 连不上服务                           | 输出「工作台不可达」，结束本轮（service_unreachable），不要循环重试             |

## 7. `blocked` 里的原因码

| 码             | 含义                                                                                                                               |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `doing`        | 项目里已有进行中的任务（可能是别的 agent，也可能是等你回答）                                                                       |
| `review`       | 项目里有交付在等用户验收                                                                                                           |
| `dirty`        | 项目有未提交改动（可能是上一轮你的改动，等用户提交）                                                                               |
| `path_missing` | 项目目录不存在（或路径不是目录）                                                                                                   |
| `git_timeout`  | 检查工作区超时（网络盘 / 仓库锁）                                                                                                  |
| `cooldown`     | 这条需求你刚释放过，冷却期内不会再派给你                                                                                           |
| `locked`       | 项目里有你（或别人）认领了还没交付的任务，项目被锁着，等用户在需求详情里点「解锁项目」。这时**不要重试、不要换名字**，结束本轮即可 |

都不用你处理。打印出来让人看到就够了，也不要自己 `git commit` 去「清干净」再取活。

## 8. 硬边界

- 一轮只做一个任务：一次 `/next`；交付可以多轮（收到 `feedback` 继续改并再次 `/complete`），最后以通过、超时或 `/release` 收尾，不要在一次运行里连续领活。
